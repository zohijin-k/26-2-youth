# JBAI LLM 안정화

Source: 팀장 요청 2026-11-16 — youth(전북 청년정책 담당자 파트)에서 전북AI LLM이 붙어 있는 부분의 "범용 LLM 안정화".

## Goal

`LLM_PROVIDER=jbai`로 켠 상태에서 담당자의 "새 사업 올리기" 공고문 분석을 시연해도 되는 수준으로 만든다. 지금 문서의 권고는 "끄고 시연"이다(`docs/DEVELOPMENT.md` "JBAI 공고문 제안 시연"). 이 권고를 바꿀지 판단할 수 있는 실측 근거를 남긴다.

담당자에게 생기는 가치: 공고문을 올리면 AI가 쓴 안내문 초안과, 규칙이 찾은 기준을 뒷받침하는 AI 제안이 실제로 화면에 나온다. 실패하더라도 정해진 시간 안에 규칙 초안으로 돌아온다.

## Background

현재 구조, 실측 기록, 약점(W1~W8), 기존 시험 계약은 `research/current-state.md`에 있다. 요약:

- 대상은 공고문 분석용 `notice_llm.py`와 안내·사유 설명용 `llm_drafts.py`다. 모두 기본 꺼짐이고 실패 시 규칙 초안으로 돌아간다.
- 2026-11-16 실측에서 기준 제안은 공고문당 평균 0~0.5개만 통과했다. 버려진 이유는 거의 전부 값 불일치다.
- PR #13 이후의 안내문 작성 경로는 실제 모델로 측정된 적이 없다.

## Requirements

- **R1 실패 원인 기록** — LLM 호출이 끝날 때마다 결과 종류(정상, 시간 초과, HTTP 오류 구분, 네트워크, 형식 오류, 잘림 등), 요청 방식, 소요 시간, 시도 순번을 고정 어휘로 기록한다. 검증 단계의 결과(안내문 채택/탈락 사유, 기준 제안 받은 수·통과 수)도 기록한다. 키, 주소, 모델 이름, 요청·응답 본문, 예외 문구는 기록하지 않는다. (W1, W8)
- **R2 전체 시간 상한** — 공고문 분석 한 건에서 LLM에 쓰는 시간에 총 예산을 둔다. 예산이 부족하면 두 번째 호출을 줄이거나 건너뛴다. 호출 수 상한(최대 2회)은 유지한다. (W2)
- **R3 응답 해석 관대화** — 코드 블록, 앞뒤 설명, 여분의 키, 항목 하나의 오류 때문에 쓸 수 있는 응답 전체를 버리지 않는다. 안내문과 기준 제안에 대한 내용 검증(원문 인용, 숫자, 선정 약속, 허용 종류)은 그대로 적용한다. (W3)
- **R4 기준 제안의 값 일치 규칙** — 모델이 문장에 직접 적힌 값만 맞게 답해도 제안이 통과하도록 한다. 추출기 값과 충돌하는 값, 후보에 없는 키, 무관한 인용은 지금처럼 통과시키지 않는다. 제안은 여전히 기존 자동 후보에만 붙고, 규칙 후보의 값은 바뀌지 않는다. (W4)
- **R5 프롬프트 정리** — 종류별로 쓸 값의 키를 고정 문구로 알려 주고, 계산값은 쓰지 않게 하며, 안내문 길이를 제한한다. 프롬프트에 규칙 후보나 신청자 정보는 넣지 않는다. (W4, W6)
- **R6 입력·출력 길이 관리** — 모델에 보내는 공고문 길이에 상한을 두고, 잘린 응답을 감지해 실패로 분류한다. (W5, W6)
- **R7 실측** — 작업 전(main)과 작업 후(작업 브랜치)를 같은 합성 공고문 3종, 같은 명령으로 실제 호출해 비교한다. 공개 합성 글자만 보내고, 결과에는 상태·방식·개수·초만 남긴다.
- **R8 문서와 규격** — `docs/DEVELOPMENT.md`(와 같은 문단을 가진 `README.md`, `demo/README.md`), `.env.example`, `.trellis/spec/backend/notice-drafts.md`를 새 동작과 실측 수치로 갱신한다. 의도적으로 바꾼 시험 기대값을 목록으로 남긴다.
- **R9 불변 조건** — 기본값 `none`에서 외부 호출 0. 공급자에게 가는 것은 공개 공고문 글자와 부가 설명문뿐. 판정 규칙과 규칙 후보 불변. AI가 쓴 안내문과 제안은 담당자 확인 전까지 미확정. 검증에서 탈락한 내용은 화면에 들어가지 않는다. 프런트와 보호 파일 10개는 수정하지 않는다.

## Acceptance Criteria

실측 기준은 합성 공고문 A·B·C를 `json_object` 방식으로 4회씩, 총 12회 호출한 결과다.

- **AC1 (R3, R7)** 형식이 맞아 해석 가능한 응답이 12회 중 11회 이상.
- **AC2 (R2)** 공고문 분석 한 건의 LLM 구간이 총 예산을 넘지 않는다. 기본 예산은 40초 이하(지금은 최악 60초)로 두고, 가짜 시계 시험으로 보장한다. 실측 최대 소요 시간을 보고한다.
- **AC3 (R3, R5, R7)** AI 안내문 초안이 검증을 통과해 안내문 칸에 들어가는 경우가 공고문마다 4회 중 3회 이상.
- **AC4 (R4, R5, R7)** 검증을 통과한 기준 제안이 3종 모두 평균 1개 이상(기준선 0.0 / 0.0 / 0.5).
- **AC5 (R9)** 검증에서 탈락한 내용이 화면에 들어간 경우 0(확인 도구의 "화면 위반" 0).
- **AC6 (R1)** 가짜 transport 시험에서 실패 종류별로 정해진 어휘가 기록되고, 로그·출력에 키·주소·본문·예외 문구가 없다.
- **AC7 (R9)** 엔진·백엔드 pytest, 시나리오 18개 모듈이 변경 전 같은 PC의 기준 결과와 같거나 좋다. 달라진 기대값은 `changed-test-expectations.md`의 목록과 정확히 일치한다. 프런트 파일 변경 0.
- **AC8 (R9)** `LLM_PROVIDER=none` 또는 설정 불완전 시 호출 0(기존 시험 유지).
- **AC9 (R8)** 문서와 규격이 새 동작·새 수치와 일치하고, 시연 권고(켬/끔)가 실측 결과를 근거로 적혀 있다.

AC1, AC3, AC4는 실제 모델에 달려 있어 코드만으로 보장할 수 없다. 미달하면 원인(분류 기록)과 함께 그대로 보고하고 권고를 "끔"으로 유지한다.

## Out of Scope

- 전북AI가 아닌 다른 LLM 공급자 지원(공급자 일반화).
- 담당자 화면에 "AI 초안 실패" 상태를 표시하는 일. 실패 원인은 서버 기록으로만 남긴다.
- 전북AI OCR, 규칙 추출기(`notice_analysis.py`)의 추출 로직, 판정 규칙.
- 안내문 검증 기준(원문 인용, 숫자, 선정 약속)을 느슨하게 하는 일.
- LLM이 규칙이 못 찾은 새 기준을 제안하게 하는 일(규격상 금지).
- 시연에서 실제로 켤지에 대한 최종 결정. 이 태스크는 근거와 권고까지만 낸다.

## Key Decisions

- **D1 범위** — "전북AI를 켠 채 안정화"(2026-11-16 팀장 선택). 다른 LLM 지원은 제외.
- **D2 값 불일치** — 이번에 해결한다(2026-11-16 팀장 결정). 방식은 "문장에 직접 적힌 값만 비교": 모델이 쓴 값이 모두 후보의 값과 같고, 그 종류의 핵심 값이 빠짐없이 있으면 통과. 대안이던 "인용만으로 연결"은 값이 충돌해도 통과시킬 수 있어 택하지 않는다.
- **D3 실패 표시** — 화면이 아니라 서버 기록으로 남긴다(프런트 무변경).
- **D4 호출 수** — 분석 한 건당 최대 2회(현행 유지). 같은 방식 재시도는 추가하지 않고 기존 "다음 방식으로 한 번"을 총 예산 안에서 쓴다.

## Risks

- 실제 모델의 응답 품질이 기준(AC1, AC3, AC4)에 못 미칠 수 있다. 이 경우 프롬프트 조정까지 하고도 미달이면 권고는 "끔"으로 남는다.
- 이 PC(Windows)에서 전체 시험 게이트가 원래 통과하는지 기록이 없다. 변경 전에 기준 결과를 먼저 잡는다.
- 실측에는 팀장의 전북AI 키와 실제 호출 약 24~30회가 필요하다. 호출은 매번 승인 후 실행한다.
