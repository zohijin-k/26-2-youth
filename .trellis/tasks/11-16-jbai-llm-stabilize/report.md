## 5. 계획과 달라진 점

1. 의도적으로 바꾼 기존 시험이 2곳이 아니라 3곳이다.
2. 총 예산 기본값을 25초로 낮추지 않고 40초로 뒀다(`design.md` 6절). 처음에는 시연 설정으로 25초를 권고했으나, 실제 공고문에서 응답이 최대 21.6초여서(8절) 그 권고는 철회한다.
3. 프롬프트 조정 뒤 재실측은 하지 않았다. 첫 작업 후 실측이 기준을 넘었다.
4. `.env.example`의 `JBAI_RESPONSE_FORMAT` 주석이 기본값을 `json_schema`로 잘못 적고 있어 `json_object`로 고쳤다.

## 6. 시연 권고

**켠 상태로 시연할 수 있다.** 근거는 2절, 3절, 7절, 8절이다.

- 설정: `LLM_PROVIDER=jbai`, `JBAI_BASE_URL`, `JBAI_API_KEY`, `JBAI_TEXT_MODEL`. 총 예산은 기본값(40초)을 그대로 둔다. `JBAI_ALLOW_REAL_DOCS`는 비워 둔다(OCR은 로컬).
- 실제 공고문에서 효과가 있는 것은 AI 안내문이다. 기준 제안은 합성 공고문에서만 붙고 실제 공고문에서는 붙지 않았다(8절). 시연에서 기준 제안 카드를 보여 주려면 합성 공고문을 써야 한다.
- 실제 공고문은 분석에 8~22초가 걸린다. 전북AI가 느린 날에는 상한(40초)까지 걸릴 수 있다.
- 실패해도 규칙 초안이 그대로 나오므로 시연 흐름은 끊기지 않는다. 원인은 백엔드 콘솔의 `llm_call` 줄로 확인한다.

## 7. 화면 확인 (2026-11-17, 실제 호출 1회)

- 방법: 격리 서버(임시 DB와 저장소, `LLM_PROVIDER=jbai`, `JBAI_LLM_BUDGET_SEC=25`)와 프런트를 띄우고, 담당자로 로그인해 "새 사업 올리기"에서 합성 공고문과 서식 PDF를 올려 분석했다. 저장소의 `demo.db`와 `storage`는 쓰지 않았다.
- 서버 기록: `llm_call purpose=notice_analysis mode=json_object attempt=1 outcome=ok seconds=3.7`, `llm_result purpose=notice_analysis guidance=accepted criteria_received=3 criteria_accepted=3`.
- 화면: ② 안내문에 AI가 쓴 안내문이 들어가고 "AI 작성 · 공고문과 대조 필요" 칩이 붙었다. "추가 안내 3개" 안에 "AI 제안 · 담당자 확인 필요" 카드 3개(나이, 거주지, 서류 발급일)가 나왔다. 확인하지 않은 항목이 남아 "올리기(게시)" 버튼은 눌리지 않는다.
- 브라우저 콘솔 오류는 로그인 전 세션 확인의 401 두 건뿐이다.
- 확인하지 않은 것: 제안 카드에서 "항목 확인하기"로 기준을 확정하고 게시하는 뒤쪽 흐름, 실제 공고문.

## 8. 실제 공고문 측정 (2026-11-17, 실제 호출 10회)

공개된 실제 공고문 PDF 3종을 `json_object` 방식으로 3회씩 호출했다(9회). 채택된 안내문의 문장을 보려고 두배적금 공고문으로 1회 더 호출했다. 보낸 것은 공고문 글자뿐이다. 수치는 `measure-real-notices.json`에 있다.

|---|---|---|---|---|---|---|

- **호출**: 10회 모두 HTTP 200, 해석 가능, 시간 초과 0. 합성 공고문(2.8~8.7초)보다 느리다(7.6~21.6초).
- **안내문**: 10회 모두 채택. 두배적금 공고문에서 채택된 초안은 사업 목적, 지원 대상, 지원 내용, 모집 인원, 신청 기간, 신청 방법, 문의처를 7줄로 정리했다. 같은 공고문의 규칙 초안은 제목 자리가 비고, 2단으로 편집된 PDF의 글자 순서가 섞여 서로 다른 문장이 한 줄에 붙어 있었다.
- **기준 제안**: 통과 0. 받은 제안 30건은 모두 원문 인용이 맞았다(인용 불일치 0, 값 불일치 0). 그런데 27건은 인용한 문장이 추출기에서 자동 규칙이 아닌 체크리스트 후보였고, 3건은 추출기 후보가 없는 문장이었다. 규격상 제안은 자동 후보에만 붙는다.
- **추출기가 실제 공고문에서 자동 후보를 거의 만들지 못하는 이유**: 한 줄에 조건이 여러 개 섞임(나이와 소득, 거주와 나이), 한 줄에 날짜가 셋 이상, 시군 단위 거주, 엔진의 기준표와 다른 중위소득 비율, 2단 편집 때문에 서로 다른 문장이 한 줄로 붙음. 세 공고문 모두 제목 후보도 찾지 못했다.
- **화면 위반**: 0.

판단: 호출 안정성과 안내문 작성은 실제 공고문에서도 성립한다. 기준 제안은 합성 공고문에서만 효과가 있고 실제 공고문에서는 붙을 자리가 없다. 원인은 LLM 쪽이 아니라 규칙 추출기의 적용 범위이며 이 태스크의 범위 밖이다.

## 9. 사람이 결정할 것

1. 시연과 제출물에서 실제로 켤지. 켠다면 발표 자료의 "LLM은 기본 꺼짐, 끄고 시연 권장" 설명을 바꿔야 한다.
2. 실제 공고문에서 기준 제안이 붙지 않는 문제를 어떻게 할지. 선택지는 (가) 규칙 추출기를 실제 공고문에 맞게 보강(진행 중인 추출 규칙 보강 과제), (나) 체크리스트 후보에도 AI 제안을 "참고"로 보여 주도록 규격 변경, (다) 기준 제안은 그대로 두고 AI 안내문만 내세움.
3. 이 PC에서 원래 실패하는 시험(엔진 10, 백엔드 133+2, `run_p17`)을 따로 다룰지.
