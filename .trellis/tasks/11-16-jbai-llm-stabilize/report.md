## 2. 실측 (합성 공고문 3종 × 4회, `json_object`)

| 공고문 (자동 기준 수) | 작업 전: 통과 합계 | 작업 후: 통과 합계 | 작업 후: 안내문 채택 | 작업 후: 기준 제안 통과 |
|---|---|---|---|---|
| A (4) | 1, 1, 1, 1 | 5, 5, 5, 5 | 4/4 | 4, 4, 4, 4 |
| B (2) | 0, 1, 1, 0 | 3, 3, 3, 2 | 3/4 | 2, 2, 2, 2 |
| C (1) | 1, 1, 1, 1 | 2, 2, 2, 2 | 4/4 | 1, 1, 1, 1 |

- 통과 합계는 안내문 초안과 기준 제안을 합친 수다. 작업 전 도구는 둘을 나눠 세지 못한다. 작업 전에는 받은 제안의 값 불일치가 A 4건, B 3건, C 1건씩 매회 나왔다.
- 응답: 24회 모두 HTTP 200, 해석 가능. 작업 전 1.41~8.72초(평균 5.0초), 작업 후 2.80~8.03초(평균 5.5초). 시간 초과 0.
- 작업 후에 버려진 제안은 3건이다(B 2회차·3회차, C 3회차에 각 1건, 모두 값 불일치). 자동 후보 수보다 하나 더 온 제안이며 화면에는 들어가지 않았다.
- B 4회차는 모델이 안내문을 주지 않았다(`guidance=none`). 이때는 규칙으로 만든 안내문이 그대로 나온다.
- 긴 합성 공고문: 전체 48,635자 중 앞 30,000자 전송, HTTP 200, 6.32초, 안내문 채택, 기준 제안 4/4.
- 화면 위반(검증에서 탈락한 내용이 결과에 들어간 경우) 0.

## 5. 계획과 달라진 점

1. 의도적으로 바꾼 기존 시험이 2곳이 아니라 3곳이다.
2. 총 예산 기본값을 25초로 낮추지 않고 40초로 뒀다(`design.md` 6절). 시연 설정으로 `JBAI_LLM_BUDGET_SEC=25`를 권고한다.
3. 프롬프트 조정 뒤 재실측은 하지 않았다. 첫 작업 후 실측이 기준을 넘었다.
4. `.env.example`의 `JBAI_RESPONSE_FORMAT` 주석이 기본값을 `json_schema`로 잘못 적고 있어 `json_object`로 고쳤다.

## 6. 시연 권고

**켠 상태로 시연할 수 있다.** 근거는 2절과 3절이다.

- 설정: `LLM_PROVIDER=jbai`, `JBAI_BASE_URL`, `JBAI_API_KEY`, `JBAI_TEXT_MODEL`, 권장 `JBAI_LLM_BUDGET_SEC=25`. `JBAI_ALLOW_REAL_DOCS`는 비워 둔다(OCR은 로컬).
- 한계: 합성 공고문 3종·12회 규모다. 실제 공고문 PDF(길이, 표, 줄바꿈)에서는 재지 않았다. 전북AI가 느린 날에는 분석이 상한까지 걸릴 수 있다.
- 실패해도 규칙 초안이 그대로 나오므로 시연 흐름은 끊기지 않는다. 원인은 백엔드 콘솔의 `llm_call` 줄로 확인한다.
