## 2. 실측

### 2.1 실제 공고문 3종 × 3회 (`json_object`)

| 공고문 | 응답 시간 | 안내문 채택 | 받은 제안 | 자동 후보에 붙음 | AI 참고 | 참고가 된 종류 |
|---|---|---|---|---|---|---|
| 두배적금 (8쪽) | 10.4~13.8초 | 3/3 | 4, 4, 6 | 0, 0, 0 | 3, 3, 4 | 나이·거주지·중위소득 3회, 서류 발급일 1회 |
| 직무인턴 (8쪽) | 7.1~12.6초 | 3/3 | 2, 2, 2 | 0, 0, 0 | 2, 2, 2 | 나이·거주지 3회 |
| 청년월세 (6쪽) | 7.9~11.7초 | 3/3 | 4, 3, 4 | 0, 0, 0 | 3, 2, 3 | 나이·중위소득 3회, 거주지 2회 |

- 9회 모두 HTTP 200. 받은 제안 31건 중 24건이 참고가 됐다. 어제는 같은 공고문에서 붙은 제안이 0건이었다.
- 참고가 되지 못한 7건: 인용이 원문과 다름 3건(두배적금, 근로 계속성), 추출기 후보가 없는 문장 1건(두배적금, 근로 계속성), 추출기가 읽은 값과 다름 3건(청년월세, 중위소득).
- 화면 위반(검증에서 탈락한 내용이 결과에 들어간 경우) 0.

### 2.3 화면 확인 (1회)

전북AI를 켠 격리 서버(임시 DB·저장소)에 실제 두배적금 공고문을 올렸다. 기록은 `outcome=ok seconds=19.2`, `guidance=accepted criteria_received=5 criteria_accepted=0 criteria_reference=4`였다.

| 카드의 칩 | AI가 읽은 조건 | 근거 쪽 |
|---|---|---|
| AI 참고 · 담당자가 직접 확인 | 거주지 · 전북특별자치도 | 1 |
| AI 참고 · 담당자가 직접 확인 | 나이 범위 · 18~39세 | 1 |
| AI 참고 · 담당자가 직접 확인 | 중위소득 · 140% 이하 | 1 |
| AI 참고 · 담당자가 직접 확인 | 서류 발급일 · 2026-03-03 | 2 |

- 네 값 모두 공고문 내용과 맞다. 화면에서 따로 본 나이 항목은 "담당자 확인"과 미확인 상태 그대로였고(나머지 세 항목은 화면에서 따로 보지 않았다) 게시 버튼은 비활성이었다.
- "작성 중 저장"은 200으로 끝났다. 저장한 뒤에는 카드가 남지 않는다(기존 제안 카드와 같은 동작, prd Out of Scope).
- 확인하지 못한 것: "항목 확인하기" 버튼의 화면 이동. 브라우저 창이 가려진 상태라 스크롤을 볼 수 없었다. 이동 대상 요소는 있었고 이 버튼의 코드는 바꾸지 않았다.

## 5. 계획과 달라진 점

- 의도적으로 바꾼 기존 기대값은 3곳이 아니라 2곳이다(`changed-test-expectations.md`). `llm_result` 줄을 비교하는 곳이 두 군데뿐이었다.
- 계획에 없던 시험 1개를 더했다: 참고가 든 초안을 저장하면 참고 없는 초안과 같은 결과가 저장된다.
- 프런트 규격(`program-authoring.md`)은 고치지 않았다. 제안 카드에 대한 기존 서술이 없어, 표시 계약은 백엔드 규격의 참고 제안 항목에 함께 적었다.

## 6. 남은 한계

- **한 문장에 같은 종류의 조건이 둘이면 하나만 나온다.** 청년월세 공고의 `청년가구 기준 중위소득 60% 이하 / 원가구 기준 중위소득 100% 이하`에서 추출기는 60%로 읽는다. 모델이 100%로 읽은 제안은 "추출기가 읽은 값과 다름" 규칙으로 표시되지 않았다(3회 모두). 카드에는 60%만 나온다.
- 근로 계속성 조건은 한 번도 참고가 되지 못했다(4건: 인용 불일치 3, 추출기 후보 없는 문장 1).
- 모델이 문장에 적힌 값을 다른 뜻으로 읽을 가능성은 남는다. 참고 카드는 인용 문장과 값을 함께 보여 주고, 확정은 담당자가 한다.
- 참고 카드는 분석 직후에만 보이고 저장하면 사라진다.
- 추출기가 제목을 찾지 못하는 문제, 자동 후보가 적은 문제는 이 작업 범위 밖이다.
